# Sesión 2026-10-28 — Notación Tekken ↔ botones ↔ `_raw.json` y `on block` / `on hit`

Estado: **implementado y validado offline**. El HUD enseña el `on block` y el
`on hit` reales de la tabla, y cuando el `on hit` es `KND` publica `KND` en vez
de inventar frames.

---

## 1. Lo que pidió el usuario

> «buscar exhaustivamente lo que se llama TEKKEN NOTATION, emparejarlo con los
> comandos asociados a cada botón del juego ("círculo es 4, cuadrado es 1") y
> enlazar todo eso con los `_raw.json` […] para poder identificar correctamente
> tanto el input como la información real específica de cada movimiento […]
> importa reflejar las frames on block y on hit, y si `on_hit` dice `KND` se
> deja como `KND` en vez de calcular cuántas frames pasan.»

Contexto: al hacer `df+3` (bajo, `i27`, `on block −29`, `on hit KND`) el HUD no
enseñaba esos datos: el ID no estaba mapeado y el nombre que salía no era el
golpe.

## 2. Referencia

- <https://wavu.wiki/t/Notation> — estilo de la comunidad (botones, direcciones,
  mociones, mayúscula = mantener, `+` / `,` / `~` / `*`, posturas).
- <https://tekkendocs.com/t6/bryan> — origen de `data/raw/`.

## 3. Qué se añadió

### `tools/tekken_notation.py`

Motor de notación con:

- tabla de botones PSP (`1`=cuadrado, `2`=triángulo, `3`=cruz, `4`=círculo);
- direcciones, diagonales, mociones (`qcf`, `qcb`, `hcf`, `hcb`, `dp`, `rdp`,
  `ff`, `bb`) y posturas (`FC`, `WS`, `BT`, `SS`, `OTG`, `FUFT`… + las de cada
  personaje);
- tokenizador tolerante: `1,2` son dos golpes y `1+2` uno simultáneo;
  `f,n,d,df+3` es una moción; `f,F+2` conserva la mayúscula (mantener);
- `canonical()` → la forma que usan los `_raw.json`
  (`DF+3`→`df+3`, `ws + 2`→`ws2`, `fc.4`→`FC.4`);
- `psp_steps()` → la entrada paso a paso (`qcb+3` = abajo → abajo+izquierda →
  izquierda+cruz);
- enlace con el catálogo: `load_moves`, `find_key`, `lookup`, `format_move`;
- CLI: `--tables`, `--check-raw`, `--stances`, `--match`, `--buttons`,
  `--canonical`, `--steps`.

**Cobertura:** `--check-raw` recorre los 38 `_raw.json` (5782 entradas, incluido
`jack-6`, que se quedaba fuera por el guion del nombre) y da **100 %** de
estructura válida, 0 ilegibles. Los 52 tokens fuera del vocabulario son
abreviaturas de postura de personaje (`RLX`, `SNK`, `DCH`, `DRU`, `DRG`…) y se
aceptan tal cual; los 67 `Left throw`/`Right throw`/`Back throw` se detectan como
*nombre*, no como notación.

### HUD

- Etiquetas en forma canónica (`Tracker._note` y `notation_for`).
- `FrameDisplayData` lleva `block_str` / `hit_str` (`on block` / `on hit` de la
  tabla) y `table_str` → `b-29 hKND`.
- Overlay: nueva celda de tabla a la derecha (`W` 620 → 700), en gris.
- Consola (`--debug`): `… [544->562]  tabla b-14 h+2`.
- `KND` sigue mandando: si el `on_hit` es cualitativo, la ventaja medida no se
  publica (`3+4 i18 — KND`).
- `--no-names`: quita el nombre y deja solo lo medido + `b/h`.
- `--replay` ya no choca con el mutex de instancia única (la demo no toca
  PPSSPP).

### `--learn`

Antes de guardar el mapeo enseña la ficha real:

```
[learn] df+3: i27  b-29  hKND  (down, right, cross)
```

y guarda la forma canónica, no lo que se haya escrito a mano.

En la sesión en vivo el ID `18` apareció con tres medidas distintas
(`i12 +4`, `i16 +15`, `i17 +2`) → son tres movimientos que el juego comparte en
ese ID (`ws3`, `b+4`, `f+3`); un solo nombre no puede cubrirlos.

## 5. Límite

La notación enlaza **input ↔ botones ↔ ficha**, no adivina qué Move ID es qué.
Si el ID no está en `data/mappings/<personaje>_map.json`, el HUD no tiene
`on block` / `on hit` que enseñar y sigue mostrando `#id`. `--match` y
`--learn` son el camino para cerrarlo.
